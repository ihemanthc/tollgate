# Tollgate routing labels

Each row is one user query labelled with its **minimum sufficient tier**: the cheapest of three
model tiers (`local_small`, `mid_tier`, `frontier`) whose answer an LLM judge rated as good as
the frontier tier's answer. Tollgate fine-tunes a router on these labels to send each query to
the cheapest model that can handle it.

Blocks marked `tollgate:begin`/`tollgate:end` are generated by `tollgate push-dataset` from the
code and the data. No number in this card is written by hand.

## Labelling procedure

1. **Answers.** Every query is answered once by each tier at temperature 0, capped at 4096
   output tokens (reasoning tokens included); the judge has the same cap. Calls are cached by
   sha256(prompt, model), so no query is answered twice by the same model, except that a reply
   which ran into an earlier, lower cap is asked again under the higher one.
2. **Judging.** For each cheaper tier (`local_small`, `mid_tier`), an LLM judge sees the
   question, the frontier answer as the *reference* and the cheaper answer as the *candidate*.
   It returns one of:
   - `equivalent`: same substance as the reference (same final answer, key facts or steps);
     only wording, length or formatting differ.
   - `acceptable`: different or less thorough, but correct and complete enough that the user
     would be satisfied.
   - `worse`: wrong, missing something the user needs, unsafe, off-topic, or a refusal the
     reference did not make.

   Output is forced to JSON and validated. One retry is allowed on unparseable output. A verdict
   that still fails is recorded as missing, never guessed.
3. **Label.** `tier` is the cheapest tier judged `equivalent` or `acceptable`, or `frontier`
   if none was. A cheap tier that passes wins even if a pricier tier was judged `worse`.
4. **Dropped rows.** A query is left out if its frontier answer failed, or if any tier cheaper
   than its label has no verdict. Such a tier might have been sufficient, so its label could be
   too expensive.
5. **`needs_tools` / `needs_rag`.** These are not judged. They are regex heuristics over the
   frontier answer (tool-call markup, "I can't browse", knowledge-cutoff phrasing) and are
   placeholders until hand labels replace them.

## The judge is never the frontier model

The judge must not be the model that wrote the frontier answer. The reference in every
comparison is the frontier answer, so a frontier-model judge would be grading candidates against
its own output. LLM judges prefer their own generations (self-preference). That would mark more
cheap answers `worse`, push labels up to `frontier`, and train a router that overspends.

Models are compared by base name (`openai/gpt-4o` and `azure/gpt-4o` are the same model). The
rule is enforced when collecting (`tollgate collect-all`, `tollgate judge`) and again when
publishing: `tollgate push-dataset` refuses if any verdict for these rows came from a frontier
model. It does **not** exclude other models from the frontier model's family or vendor; see
below.

## Known judge biases

None of these has been measured on this dataset yet. They are the known failure modes of
single-judge LLM labelling, applied to this setup.

- **Position.** The reference is always shown before the candidate, never in swapped order, so
  any position preference of the judge is uncorrected.
- **Family and self-preference.** The judge may favour answers from its own model family or
  vendor. If it shares a family with the mid tier, `mid_tier` labels may be inflated.
- **Verbosity.** LLM judges tend to rate longer answers higher. Cheaper tiers often answer more
  briefly, which pushes labels up.
- **Reference anchoring.** Candidates are judged against the frontier answer. The prompt asks
  for judgement against the question, but a correct cheap answer that disagrees with a wrong
  reference can still be rated `worse`.
- **The `acceptable` boundary.** It is subjective, and it counts as sufficient: a lenient judge
  pulls labels down.
- **One judgement per pair.** There is a single sample at temperature 0, no second judge, and no
  human audit yet.
- **Missing verdicts.** Queries whose verdicts failed to parse can be dropped (step 4 above),
  which can bias the sample toward questions that are easy to judge.
- **Language.** LMSYS prompts span many languages, and judge quality outside English is less
  certain.

## Splits

Rows are split 70/15/15 into train, calibration and test, stratified by (label, source) with a
fixed seed. Each stratum splits to within one row. The calibration split is reserved for fitting
the router's temperatures and is never used in training. Early stopping uses a holdout carved
out of train.

## Rebuilding withheld text

For rows with `text_included = false`, `text_sha256` is sha256 of the exact UTF-8 query text, as
it was extracted: for LMSYS-Chat-1M, the first user message of a conversation, with leading and
trailing whitespace stripped. With access to the source granted under its own license:

```bash
pip install pandas pyarrow datasets
huggingface-cli login
python rebuild_dataset.py --dataset dataset.parquet --out dataset.rebuilt.parquet --limit 0
```

The script streams the source at the revision listed above and fills `prompt` for every hash it
finds. `--limit 0` scans the whole source. The default `--limit` is a quick smoke test.
